# Как выкатить Alma и не разбудить меня ночью

Эта инструкция написана для владельца, а не для программиста. Каждая команда
здесь набирается целиком, ничего не надо дописывать «по смыслу», и после каждого
раздела сказано, как проверить, что получилось.

**Что было до неё.** Прод — это был один процесс `uvicorn`: одно ядро из
четырёх, без шифрования, без перезапуска при падении, без резервных копий.
Он работал. Он бы и дальше работал — ровно до первого всплеска, первого
падения или первого дня, когда кто-нибудь заметил, что данные ходят открытым
текстом.

---

## 1 · Что надо завести, и сколько это стоит

Три вещи. Больше ничего покупать не нужно.

| Что | Зачем | Сколько примерно стоит |
|---|---|---|
| **Сервер** — 4 ядра, 8 ГБ памяти, 80 ГБ диска, Linux | На нём живёт всё: приложение, база, шифрование | **€13–20 / мес** (Hetzner CPX31, Netcup) или **$48 / мес** (DigitalOcean, Vultr — то же железо, дороже) |
| **Домен** — например `api.alma.ai` | Без домена нет сертификата, без сертификата нет шифрования | **$10–15 / год** |
| **Проверка живости** — healthchecks.io | Письмо, если утренняя рассылка перестала запускаться | **$0** (бесплатного тарифа хватает: 20 проверок) |

Цены — порядок величины на середину 2026-го; проверьте на сайте, они меняются.
Разница между €15 и $48 за одинаковое железо — это разница между европейскими
хостерами и американскими, и на этом этапе она ни на что, кроме счёта, не
влияет.

### Почему именно 4 ядра и 8 ГБ

Не «на глаз». Приложение запускает по числу ядер несколько рабочих процессов
(`gunicorn.conf.py`), и каждый держит в памяти своё ядро эфемерид JPL — это
31 МБ файла плюс рабочие массивы, порядка 300–400 МБ на процесс. Восемь
процессов — это ~3 ГБ. Плюс база (~1 ГБ при настройках из `docker-compose.yml`),
плюс запас, чтобы система не ушла в своп. 8 ГБ — это «работает с запасом»,
4 ГБ — «работает, пока не всплеск».

Ядра нужны не для сети, а для счёта: одна карта — 33 мс, один трёхдневный скан
транзитов — 112 мс (измерено), и это чистая работа процессора, которую нельзя
«подождать».

Раздел 6 — про то, когда этого перестанет хватать, с числами.

### Где взять Postgres — и это решение владельца

Два варианта, и оба нормальные.

**А. В том же `docker compose`, на том же сервере** — то, что настроено по
умолчанию. Стоит **$0**, поднимается вместе со всем остальным, и все данные
лежат на одном диске. Цена: резервные копии — ваша забота (раздел 7), и падение
сервера уносит и приложение, и базу разом.

**Б. Управляемый Postgres у хостера** — DigitalOcean Managed Database, Neon,
Supabase. **$15–60 / мес**. За эти деньги вы получаете автоматические резервные
копии, восстановление на любую минуту последних дней и чужого дежурного, когда
диск кончится. Подключается одной строкой: пропишите их адрес в
`ALMA_DATABASE_URL` в `.env` и уберите службу `db` из `docker-compose.yml`.

**Рекомендация: начать с А, перейти на Б, когда появится первая сотня
платящих.** Пока платящих нет, потеря базы — это потеря нескольких вечеров.
После — это потеря людей, которые заплатили.

## 2 · Первая установка, по шагам

На сервере (Ubuntu 24.04 или Debian 12), от пользователя с `sudo`.

**Шаг 1. Поставить Docker.**

```bash
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
# выйти и зайти заново, чтобы группа применилась
```

Проверить: `docker compose version` печатает версию.

**Шаг 2. Взять код.**

```bash
sudo mkdir -p /srv/alma && sudo chown $USER /srv/alma
git clone <адрес репозитория> /srv/alma
cd /srv/alma/backend
```

**Шаг 3. Направить домен на сервер.** В панели управления доменом — запись
типа `A` с именем `api` и значением, равным IP сервера. Проверить:

```bash
dig +short api.example.com     # должен вывести IP вашего сервера
```

Пока эта строка пустая, сертификат не выпустится, и шаг 7 не удастся.

**Шаг 4. Заполнить `.env`.**

```bash
cp .env.example .env
nano .env
```

Что обязательно (остальное — раздел 3):

```bash
# Придумывать не надо, выполните эти две строки и вставьте, что напечатает:
python3 -c "import secrets;print('ALMA_JWT_SECRET=' + secrets.token_urlsafe(48))"
python3 -c "import secrets;print('POSTGRES_PASSWORD=' + secrets.token_urlsafe(32))"
```

Для доступа к `/admin` — солёный scrypt-хэш пароля (сам пароль в `.env` не
живёт). Сгенерировать в каталоге `backend/`, пароль спросит скрыто:

```bash
python -m tools.admin_password   # напечатает ALMA_ADMIN_PASSWORD_HASH=scrypt$…
```

За доверенным краем не забыть `ALMA_TRUSTED_EDGE=true` (см. таблицу в §3).

и ещё:

```
ALMA_DOMAIN=api.example.com
ALMA_ACME_EMAIL=вы@example.com
ANTHROPIC_API_KEY=sk-ant-…
ALMA_BASE_URL=https://api.example.com
ALMA_CORS_ORIGINS=https://example.com
```

> **`ALMA_DATABASE_URL` в `.env` писать не надо.** `docker-compose.yml` собирает
> его сам из `POSTGRES_*`. Строка в `.env` его перебьёт и укажет мимо базы.

**Шаг 5. Права на файл с секретами.**

```bash
chmod 600 .env
```

**Шаг 6. Создать схему базы.**

```bash
docker compose build
docker compose run --rm --no-deps app python -m tools.migrate
# schema is up to date
```

**Это отдельный шаг, и он обязателен.** Приложение схему больше не создаёт —
оно её только проверяет и **отказывается стартовать**, если её нет. Причина в
арифметике: `gunicorn` поднимает по два рабочих процесса на ядро, то есть
восемь на этом сервере, и раньше все восемь в одну секунду выполняли по базе
`CREATE TABLE`, `CREATE INDEX` и `ALTER TABLE`. Postgres берёт под это
блокировку каталога, а наш `lock_timeout` — три секунды; семь воркеров из
восьми имели полное право не подняться, и выглядело бы это как «выкатка прошла,
сайт лежит».

Здесь работу делает один процесс. Если забыть этот шаг, следующий поднимет
воркеры, и они честно скажут, чего не хватает:

```bash
docker compose logs app | grep "run \`python -m tools.migrate\`"
```

**Шаг 7. Поднять.**

```bash
docker compose up -d --build
```

Первая сборка — 3–6 минут. Дальше сборки идут за десятки секунд.

**Шаг 8. Проверить.**

```bash
curl https://api.example.com/health
# {"status":"ok","uptime_seconds":12.3}

curl https://api.example.com/ready
# {"ready":true}
```

**`{"ready":false}` — это не «сломалось», это «чего-то не хватает».** Готовность
означает, что настроено всё, что сервис обещает: база, эфемериды, индекс мест,
ключ модели и процессор платежей. Посмотреть, чего именно не хватает:

```bash
docker compose logs app | grep "running in production without"
```

Наружу этот список не отдаётся намеренно — перечень ещё не настроенного это
готовая карта для того, кто ищет, куда ударить.

## 3 · Что вписать в `.env` — полный список

`.env.example` объясняет каждую строку на месте. Здесь — только то, без чего
не поднимется или не заработает:

| Переменная | Обязательна | Что это |
|---|---|---|
| `ALMA_JWT_SECRET` | **да** | Подпись сеансов. С заводским значением прод не стартует: любой сеанс подделывался бы кем угодно, кто читал репозиторий |
| `POSTGRES_PASSWORD` | **да** | Пароль базы. Без него `docker compose` откажется подниматься |
| `ANTHROPIC_API_KEY` | **да** | Без него прод не стартует. Расчёты работают и без ключа, но всё, что продаётся, — это вызов модели |
| `ALMA_DOMAIN` | да | Домен. По нему выпускается сертификат |
| `ALMA_BASE_URL` | да | `https://` ваш домен. Из него собираются ссылки в письмах и возврат из кассы |
| `ALMA_CORS_ORIGINS` | да | Откуда браузеру разрешено обращаться. Забыть — это работающий сервер, до которого не достучится сайт |
| `ALMA_TRUSTED_EDGE` | **да за краем** | `true`, когда перед сервисом стоит доверенный прокси (nginx в этой выкладке, Cloudflare). Только тогда читаются заголовки о клиенте: адрес (`X-Real-IP`/`CF-Connecting-IP`) для потолков по источнику и страна (`CF-IPCountry`) для валюты. **Забыть — тихая деградация:** все запросы сойдутся в один адрес прокси (общий потолок на всех) и валюта везде станет USD. **Поставить на прямом инстансе, где края нет, — дыра:** заголовки шлёт клиент, и сменой одного заголовка снимается любой потолок по источнику и подделывается цена каталога |
| `ALMA_ACME_EMAIL` | желательно | Куда писать, если продление сертификата не удаётся |
| `ALMA_BILLING_PROVIDER` + ключи | для продаж | Одно слово: `appstore`, `googleplay`, `paddle` или `dodo`. **Половина ключей хуже, чем ни одного**: сервис откажется стартовать, и это правильно — касса, которую нельзя проверить, берёт деньги и ничего не отдаёт |
| `GOOGLE_CLIENT_ID` / `APPLE_CLIENT_ID` / `RESEND_API_KEY` | хотя бы одно | Иначе аккаунт завести нечем |
| `ALMA_APNS_*` (4 штуки) | для пушей на iPhone | Все четыре или ни одной |
| `ALMA_FCM_*` (2 штуки) | для пушей на Android | Обе или ни одной |

**`.env` не попадает ни в git, ни в образ.** Это обеспечено `.gitignore` и
`.dockerignore`, и обе строки стоят там первыми не случайно: файл с секретами,
попавший в слой образа, уезжает в реестр и достаётся всякому, у кого есть образ.

## 4 · Выкатка обновления

```bash
cd /srv/alma
git pull
cd backend
docker compose build
docker compose run --rm --no-deps app python -m tools.migrate   # ← схема, одним процессом
docker compose up -d --build
```

Это всё. Приложение остановится и поднимется заново; недоступность — секунды.

**Средняя строка — не формальность, и пропустить её нельзя.** Схему приводит в
порядок один процесс до выкатки, а воркеры её только проверяют и отказываются
подниматься на базе, где не хватает таблицы или колонки. Раньше каждый из
восьми воркеров создавал недостающее сам, и на выкатке это была драка восьми
процессов за блокировки каталога Postgres (подробности — в шаге 6 раздела 2).
Проверить, не забыт ли шаг, можно в любой момент и без изменений:

```bash
docker compose run --rm --no-deps app python -m tools.migrate --check
# schema is up to date        — код возврата 0
```

Команда умеет ровно то же, что умел старт: завести недостающие таблицы,
дописать недостающие колонки и индексы. Она ничего не переименовывает и ничего
не удаляет; всё, что шире, она отказывает вслух и печатает SQL, который надо
выполнить руками.

**Что происходит с тем, кто в этот момент ждёт главу.** Рабочий процесс
получает сигнал остановиться и **две минуты** на то, чтобы доработать
(`graceful_timeout` в `gunicorn.conf.py`). Заводское значение — тридцать секунд,
и его не хватало: модель рассуждает перед тем, как писать, и наблюдался случай,
где ответ шёл три минуты. Процесс, убитый на второй, — это глава, за которую
человек заплатил и которой не получил, плюс счёт за вызов, который нам всё равно
выставлен.

Проверить после выкатки:

```bash
curl https://api.example.com/ready     # {"ready":true}
docker compose ps                      # все три службы healthy
```

## 5 · Регулярные задания — четыре штуки, и два из них никогда не запускались

В продукте есть четыре процесса, которые обязаны ходить по расписанию. **Два из
них написаны, задокументированы и ни разу не запускались:**

| Задание | Что делает | Что будет, если не запускать |
|---|---|---|
| `alma-daily` | Утренняя запись, **ежечасно** | Подписка не даёт того, за что платят |
| `alma-renewals` | Письмо за три дня до списания, раз в сутки | Обещание «предупредим за три дня» напечатано на пейволе, в FAQ, на странице условий и рядом с кнопкой оплаты — и не выполняется |
| `alma-funnel-purge` | Удаление аналитики старше 180 дней, раз в сутки | Обещание на странице приватности не выполняется |
| `alma-prune` | Чистка растущих таблиц, раз в сутки | База растёт линейно и не перестаёт никогда |

Ежечасно — потому что 10:00 наступает двадцать шесть раз вокруг света, и раз в
сутки можно быть утром только где-то одним.

Установить первые три:

```bash
cd /srv/alma/backend
sudo cp deploy/systemd/*.service deploy/systemd/*.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now alma-daily.timer alma-renewals.timer alma-funnel-purge.timer
```

### Четвёртое задание — чистка растущих таблиц

Файлов службы для него в репозитории ещё нет; они создаются двумя командами
ниже. Что оно делает и по какому обещанию — написано в самом файле
(`backend/tools/prune.py`, докстринг), и это стоит прочитать один раз: там
названы **сроки хранения и откуда взят каждый**.

Коротко: события воронки и доставки вебхуков — 180 дней (то же число, что
напечатано на странице приватности); окна ограничителей — до конца своего окна;
кэш расчётов — 180 дней. **Беседы и главы не трогаются вовсе**: про них
напечатано «пока существует ваш аккаунт», и сокращать это молча нельзя.

Посмотреть, что удалится, ничего не удаляя:

```bash
cd /srv/alma/backend
docker compose run --rm --no-deps app python -m tools.prune --dry-run
```

Поставить в расписание:

```bash
sudo tee /etc/systemd/system/alma-prune.service >/dev/null <<'UNIT'
[Unit]
Description=Alma — чистка растущих таблиц
After=docker.service
Requires=docker.service

[Service]
Type=oneshot
WorkingDirectory=/srv/alma/backend
ExecStart=/usr/bin/docker compose run --rm --no-deps app python -m tools.prune
# ExecStartPost=/usr/bin/curl -fsS -m 10 --retry 3 https://hc-ping.com/ВАШ-UUID
TimeoutStartSec=1800
UNIT

sudo tee /etc/systemd/system/alma-prune.timer >/dev/null <<'UNIT'
[Unit]
Description=Alma — чистка растущих таблиц, раз в сутки

[Timer]
OnCalendar=*-*-* 03:40:00
Persistent=true

[Install]
WantedBy=timers.target
UNIT

sudo systemctl daemon-reload
sudo systemctl enable --now alma-prune.timer
```

Время выбрано между копией базы (02:30, раздел 7) и утренним всплеском: чистка
удаляет строки, и делать это в час, когда база занята рассылкой, незачем.

Проверить, что они живы, — одна команда, и её стоит запомнить:

```bash
systemctl list-timers | grep alma
```

Она печатает, когда каждое задание запускалось в последний раз и когда
запустится в следующий. `crontab -l` печатает то, что вы *собирались* сделать;
эта команда — то, что происходит.

### Мёртвая рука — это не опция

Таймер, переставший срабатывать, невидим: логи чистые, счётчики нулевые, ошибок
нет, и первым это замечает подписчик. Лечится одной строкой.

1. Завести три проверки на <https://healthchecks.io> (бесплатно).
2. В каждом файле `deploy/systemd/alma-*.service` раскомментировать строку
   `ExecStartPost=…` и вставить свой UUID.
3. `sudo systemctl daemon-reload`.

`ExecStartPost` выполняется только после успешного завершения — упавший прогон
не пингует, а непришедший пинг превращается в письмо.

## 6 · Сколько это выдержит — арифметика

### 6.1 Утренняя рассылка: почему она шла бы часами

Исходные числа, взятые из кода и измерений, а не из головы:

| Величина | Значение | Откуда |
|---|---|---|
| расчёт карты `chart_for` | **33 мс** | измерено на машине разработки |
| трёхдневный скан транзитов | **112 мс** | там же |
| итого расчёт на одного человека | **145 мс** процессора | сумма |
| одна утренняя запись, стоимость | **$0.0143** в среднем, $0.0175 в худшем | `docs/THE-DAILY.md §2.2`, четырнадцать живых генераций |
| одна утренняя запись, время | **~10 с** (оценка, не измерение) | ~420 выходных токенов у `claude-sonnet-5`; наблюдавшийся потолок для длинной главы — 3 минуты |
| записей на человека в месяц | **10** | `rules.PER_MONTH` |
| отправок в сутки на 10 000 подписчиков | **~330** | 10 000 × 10 ÷ 30.4 |

Задание ходит ежечасно и берёт тех, у кого местные 10:00–12:59. Если бы
подписчики были равномерно размазаны по часовым поясам, в каждый прогон
попадало бы ~1 250 человек, из которых «в первый свой час» — ~420. Реальные
подписчики размазаны не равномерно: продукт русско-европейский, и половина базы
сидит в трёх соседних поясах. **Возьмём пиковый час вчетверо гуще
равномерного** — это и есть худший случай.

|  | было (строго по одному) | стало |
|---|---|---|
| расчёты в пиковый час | **5 000 × 0.145 с = 12 мин** процессора | **1 700 × 0.145 с = 4 мин** |
| генерации в пиковый час | **550 × 10 с = 92 мин** | 550 × 10 с ÷ 8 = **11 мин** |
| **прогон целиком** | **~100 минут** | **~13 минут** |

Сто минут — это дольше часа, то есть **следующий запуск таймера накладывался бы
на предыдущий**, и так по нарастающей. Утро, приехавшее к обеду, — это уже не
утро.

Что изменилось, тремя правками:

1. **Расчёты считаются последними.** Раньше карта и транзиты считались *до*
   того, как правило успевало сказать «этот человек не подписчик», «он выключил
   уведомления» или «ему уже отправлено сегодня». Большинство отказов —
   дешёвые, поэтому две трети расчётов были выброшены впустую. Это самая
   ценная из трёх правок, потому что расчёт — единственная работа здесь,
   которую нельзя делать параллельно: она занимает процессор, а не ждёт сети.
2. **Восемь получателей одновременно, а не один** (`ALMA_DAILY_CONCURRENCY`).
   Не «все разом»: тысяча одновременных запросов к модели — это 429 на всех
   сразу, а тысяча соединений к базе — это база, переставшая обслуживать сам
   сайт. Восемь держат меньше одного запроса в секунду.
3. **Отказ одного вендора больше не отменяет утро у всех.** Протухший ключ
   Firebase останавливал прогон целиком — то есть отменял утро и владельцам
   iPhone. Теперь выбывает вендор, а не прогон.

Плюс две вещи, которые видно только при аварии: **повторная выдача токена
Firebase на ответ 401** (кэш живёт 50 минут против часа, и десяти минут запаса
иногда не хватает — раньше это стоило утра всем подписчикам Android) и
**возврат дня, потерянного убитым прогоном**: деплой посреди рассылки оставлял
человеку день, который никто уже не отправит; следующий час теперь забирает его
обратно.

### 6.2 Сколько это стоит в деньгах

| Кто | Утренние записи в месяц | Счёт от Anthropic |
|---|---|---|
| 500 подписчиков (5% от 10 000 пользователей) | 5 000 | **~$72 / мес** |
| 2 000 подписчиков | 20 000 | **~$286 / мес** |
| 10 000 подписчиков | 100 000 | **~$1 430 / мес** |

Против $8.99 чистыми с подписчика: на 10 000 подписчиков это $89 900 выручки
против $1 430 на утренние записи, то есть **1.6%**. Утренняя рассылка — не то,
что разорит; разорят главы и разговор, у которых свои потолки в
`alma/config.py`.

Отправка пушей — **$0**: ни Apple, ни Google за неё не берут.

### 6.3 Когда сервера перестанет хватать

| Пользователей | Сервер | Postgres |
|---|---|---|
| до 2 000 | 2 ядра / 4 ГБ, €7 | в compose |
| **до 10 000** | **4 ядра / 8 ГБ, €15** | **в compose** |
| до 50 000 | 8 ядер / 16 ГБ, €30 | пора выносить на управляемый |
| дальше | два сервера за балансировщиком | обязательно отдельный |

**Первое, что упрётся, — процессор, а не память и не сеть.** Каждая открытая
карта — это 33 мс счёта, которые нельзя ускорить ожиданием. Признак: `docker
stats` показывает у `app` устойчиво больше 300% (то есть больше трёх ядер из
четырёх).

> **Два сервера — это отдельная работа, а не «поднять второй».** Файл-замок
> утренней рассылки (`notify/daily.single_run`) работает в пределах одной
> машины; на двух его надо переносить в базу. Пока сервер один, всё честно.

## 7 · Резервные копии — раздел, который читают слишком поздно

**Что нельзя потерять:** базу. Всё остальное — код, картинки, эфемериды —
восстанавливается из репозитория за пять минут. В базе лежат люди, их карты, их
покупки и их права.

Ежедневная копия, одной командой в `cron`:

```bash
sudo crontab -e
```

```cron
30 2 * * * cd /srv/alma/backend && docker compose exec -T db pg_dump -U alma alma | gzip > /srv/backups/alma-$(date +\%F).sql.gz && find /srv/backups -name 'alma-*.sql.gz' -mtime +14 -delete
```

```bash
sudo mkdir -p /srv/backups
```

Хранит две недели и удаляет старее.

**Копия на том же диске — это не копия.** Она спасает от «уронил таблицу» и не
спасает от «умер сервер». Настройте выгрузку в объектное хранилище (Hetzner
Storage Box — €4/мес за 1 ТБ, Backblaze B2 — $6/ТБ) или хотя бы раз в неделю
забирайте себе:

```bash
scp сервер:/srv/backups/alma-$(date +%F).sql.gz .
```

**Восстановление** (проверьте это до того, как понадобится):

```bash
gunzip -c alma-2026-08-19.sql.gz | docker compose exec -T db psql -U alma alma
```

## 8 · Логи — где смотреть, когда что-то не так

```bash
cd /srv/alma/backend

docker compose logs -f app          # приложение, в реальном времени
docker compose logs --tail=200 app  # последние 200 строк
docker compose logs proxy           # сертификат, TLS, отказы на входе
docker compose logs db              # база

journalctl -u alma-daily -n 100     # последний прогон утренней рассылки
systemctl list-timers | grep alma   # когда запускались и когда запустятся
```

Что искать:

| Строка в логе | Что значит |
|---|---|
| `daily notifications: {'due': …, 'sent': …}` | Отчёт прогона. `sent: 0` при `due: 0` — тихое небо, это нормально. `sent: 0` при `due: 400` — сломано |
| `refused:not a subscriber` и подобные | Не ошибки. Задание объясняет, почему кому-то не отправлено |
| `is out for the rest of this run` | Вендор пушей отказал. Проверьте его ключи |
| `every push vendor is out` | Отказали оба. Прогон завершился ошибкой — это увидит мониторинг |
| `running in production without: …` | Чего не хватает в настройке. Пишется на старте |
| `the database is missing …` | Забыт шаг миграции (раздел 4). Воркер не поднялся намеренно |
| `waiting for N paid conversation turn(s)` | Остановка ждёт недописанные оплаченные ответы. Норма при выкатке |
| `those answers are paid for and lost` | Ждать перестали по таймауту. Люди недосчитались ответов, за которые заплатили |
| `requests arrive from … and no edge header` | Прокси не передаёт адрес клиента, и все посетители считаются одним. Проверьте `X-Real-IP` в конфиге прокси |
| `a daily run is still in progress` | Прогон идёт дольше часа. Раз-два — не страшно; регулярно — раздел 6 |

## 9 · Откат

Если новая версия оказалась хуже старой:

```bash
cd /srv/alma
git log --oneline -5          # найти строку предыдущей версии
git checkout <строка>         # например 3f2a1b9
cd backend
docker compose up -d --build
```

Три минуты. Вернуться на свежую версию — `git checkout main` и та же последняя
команда.

**Чего откат не отменяет: изменений в базе.** Новые столбцы дописывает шаг
`python -m tools.migrate`, и старая версия их просто не замечает — это
безопасно, и **откат этот шаг повторять не надо**: схема новее кода лишних
колонок, которых старый код не знает, а обратное — код новее схемы — как раз то,
на чём воркер откажется стартовать. Но если версия успела *переписать* данные,
откат кода их не вернёт; вернёт только копия из раздела 7. Поэтому перед
большими выкатками:

```bash
docker compose exec -T db pg_dump -U alma alma | gzip > /srv/backups/before-deploy.sql.gz
```

## 10 · Что сломается первым, по опыту

1. **Сертификат не выпустился.** Причина почти всегда одна: домен не указывает
   на сервер или закрыт 80-й порт. Проверка ACME ходит именно по 80-му, и
   закрыть его «за ненадобностью» — значит остаться без продления на девяностый
   день. `dig +short ваш.домен` и `docker compose logs proxy`.
2. **Сайт не достучался до сервера.** `ALMA_CORS_ORIGINS` не содержит адрес
   сайта. Симптом обманчив: сервер работает, отвечает на `curl`, а страница
   говорит про сеть. Это браузер, а не сервер.
3. **Прод не стартует и пишет список.** Это работает как задумано: не хватает
   `ALMA_JWT_SECRET`, `ALMA_DATABASE_URL` или `ANTHROPIC_API_KEY`, и названо
   всё разом, чтобы не чинить в три захода.
4. **Таймеры не заведены.** Раздел 5. Два из четырёх заданий не запускались ни
   разу, и одно из них — единственное, что делает истинным обещание на странице
   приватности.
5. **Забыт шаг миграции.** Раздел 4, средняя строка. Симптом однозначный:
   воркеры не поднимаются и пишут в лог, чего именно не хватает и какую команду
   выполнить. Чинится в тридцать секунд — и в этом весь смысл: раньше на этом
   месте была драка восьми процессов, после которой сервис мог подняться
   наполовину и молчать об этом.
6. **Резервных копий нет.** Раздел 7. Это единственный пункт в списке, который
   нельзя починить после того, как понадобился.
