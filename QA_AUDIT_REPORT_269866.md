## HIGH

### BUG-269-001 — Т-Банк списывает НЕ рублёвую сумму: `open_session` не фиксирует RUB
Приоритет: **HIGH**
**[ИСПРАВЛЕНО]** `TBankProvider.open_session` фиксирует `currency = "RUB"` до
запроса цены: `Amount` всегда копейки рубля с полки, что бы ни разрешила страна
запроса (комментарий-«почему» с датой аудита — в коде). Без RUB-полосы
`cents_in("RUB")` бросает `NotSold` → 404 `not_sold_here` в роутере. Закреплено
тестом `test_the_amount_is_kopecks_of_the_shelf_ruble_price_no_matter_the_currency`
(проверен красным на старом коде: `Amount=499` вместо 44900); все тесты
`test_billing_tbank.py` + `test_billing_router.py` — 40 pass.
Где: `backend/alma/billing/tbank.py:459-463` (`TBankProvider.open_session`);
источник валюты — `backend/alma/api/routers/billing.py:317` +
`backend/alma/region.py:147` (`resolve`).

**Проблема.** Терминал Т-Банка списывает ровно переданное поле `Amount` (в
копейках рубля) — это его единственная валюта. Но `open_session` берёт сумму из
каталога по **разрешённой валюте запроса**, без проверки, что это RUB:

```python
item = prices.product(product)
cents, display = item.cents_in(currency), item.display(currency)   # <-- currency любой
...
fields = {"Amount": cents, "OrderId": order_id, ...}               # Amount уходит как рубли
```

`currency` приходит из `billing.py:317 → region.resolve(stated=country, edge=edge)`,
а `resolve` (`region.py:147`) отдаёт приоритет edge-заголовку над `stated`:
`return clean_country(edge) or clean_country(stated)`. Поэтому `country:"RU"`,
который жёстко шлёт страница `/pay`, **перебивается** любым краевым заголовком
(`CF-IPCountry` при `ALMA_TRUSTED_EDGE=true`) — а при отсутствии страны вовсе
`currency_for(None)` = **USD**.

**Что происходит на деле (живой расчёт, `alma.billing.catalogue`):**

| resolved currency | `cents_in` (door.natal) | Amount в Init | Спишется Т-Банком |
|---|---|---|---|
| RUB (верно) | 44900 | 44900 коп | **449.00 ₽** |
| USD (нет страны) | 499 | 499 коп | **4.99 ₽** |
| EUR | 549 | 549 коп | 5.49 ₽ |
| INR | 10900 | 10900 коп | 109.00 ₽ |
| bundle.static USD | 1999 | 1999 коп | 19.99 ₽ (вместо 1799 ₽) |

После списания вебхук считает `_the_money_covers_it` уже по **RUB**
(`tbank.py:283` жёстко `currency="RUB"`): 499 < 44900 → грант НЕ выдаётся
(`provider.py:1037`). Итог наихудшего рода: **покупатель заплатил произвольную
мелкую сумму, касса пробила чек 54-ФЗ на неё, а доступа он не получил.**

**Как воспроизвести.**
1. Деплой с `ALMA_BILLING_PROVIDER=tbank` (русский сайт).
2. `POST /v1/billing/checkout {"product":"door.natal"}` **без** `country`
   (или с `country:"US"`, или легитимный `country:"RU"`, но `ALMA_TRUSTED_EDGE=true`
   и краевой заголовок сообщает не-RU — типично для российского пользователя за
   VPN/прокси).
3. Уход на форму Т-Банка с `Amount=499` → списание 4.99 ₽.
4. Вебхук `CONFIRMED, Amount=499` → `_the_money_covers_it` = false → грант не выдан.

Ожидается: Т-Банк всегда выставляет рублёвую цену полки (449 ₽), либо чекаут
отказывает, если валюта не RUB.
Фактически: сумма зависит от разрешённой страны; не-RUB даёт мисчардж + отказ доступа.
Доказательство: `qa_evidence/tbank_amount_bug.txt` (живой расчёт `cents_in` по
валютам + цепочка кода); каталог: `curl …?country=US → USD`, `?country=IN → INR`.

**Что исправить (точечно, один файл).** В `backend/alma/billing/tbank.py`,
`TBankProvider.open_session`, зафиксировать валюту рублём независимо от аргумента:

```python
async def open_session(self, *, product, user_id, currency, country=None, email=None):
    from . import catalogue as prices
    currency = "RUB"                       # <-- терминал Т-Банка списывает только рубли;
    item = prices.product(product)         #     разрешённая страна не смеет выбрать другую
    cents, display = item.cents_in("RUB"), item.display("RUB")
    ...
```

(`item.cents_in("RUB")` бросит `NotSold`, если RUB-полосы нет, — роутер уже
превращает это в 404 `not_sold_here`, что и нужно.) Альтернатива уровнем выше:
в `billing.py:checkout` для адаптера `tbank` брать валюту из адаптера, а не из
`region.resolve`.

Фактически: правые ~19–34px срезаны, скролла к ним нет.

`qa_evidence/pay-shop-390-ok.png` и `pay-shop-1280.png` (шире — чисто).

**Что исправить.** Разрешить перенос у блочной кнопки — в `src/app/screens.css`
добавить:

```css

```

(или медиазапрос `@media (max-width: 360px) { .btn-block { white-space: normal; } }`,
или укоротить подпись до «Обновить доступ»). Только это снимает распор — карточки
и заголовок сами по себе в 261px помещаются.

## LOW / требует проверки

### OBS-269-003 — Веб-чекаут доверяет клиентской стране при выборе валюты (корень BUG-269-001)
Приоритет: LOW (для Paddle/Dodo — требует проверки price-id)
**[НЕ ИСПРАВЛЕНО: не воспроизводимо на стенде — требуется Paddle/Dodo-санбокс]**
Денежная половина для Т-Банка закрыта на уровне адаптера (BUG-269-001: валюта
зафиксирована рублём, разрешённая страна на `Amount` больше не влияет). Для
Paddle/Dodo `processor_ids` пусты, чекаут в dev отдаёт 503 без ключей —
проверить, списывает ли процессор по адресу карты или по нашей сумме, локально
нечем. Каталог (`?country=`) — витринная оценка по докстрингу `region.py`;
менять `region.resolve` вслепую — риск сломать законную PPP-витрину без
возможности проверить денежный путь. Оставлено до санбокса владельца.
Где: `backend/alma/api/routers/billing.py:317`, `backend/alma/region.py:147`.

`region.resolve` использует клиент-переданный `country` (тело/квери) как фолбэк,
когда край молчит. На денежном пути это значит: отправитель запроса может выбрать
валюту каталога. Подтверждено на каталоге: `?country=IN → INR ₹109`,
`?country=US → USD`. Для **Т-Банка** это конкретный подтверждённый HIGH выше.
Для Paddle/Dodo `region.py` (докстринг, строки 56-60) утверждает, что реально
списывает валюту процессор по адресу карты, а наш каталог лишь «оценка для
витрины». Это **верно только если** у каждого товара заведены раздельные price-id
на валюту и процессор берёт валюту по адресу, а не по нашей сумме. Сейчас
`processor_ids` пусты (ничего ещё не продавалось), поэтому динамически
недостижимо. **Проверить на сконфигурированном Paddle/Dodo-санбоксе:** открыть
чекаут с `country:"IN"` из США и убедиться, что процессор списывает по адресу
карты, а не по нашей INR-сумме. Если по нашей — это недоплата $4.99 → ₹109.

Доказательство: `qa_evidence/tbank_amount_bug.txt` (та же цепочка resolve).

  двоих, что закон разрешает и что помечено комментарием). Ноль нарушений.
  Русские письма (`backend/alma/mail.py`): 0 формальных «вы».
- **Французский узкий неразрывный пробел.** `src/lib/i18n/fr.ts`: 31×U+202F,
  0×U+00A0; «подозрения» скрипта — это тернарный оператор JS `? :`, ложные.
- **Полнота писем.** Все 9 локальных словарей `mail.py` (SUBJECTS, BODIES,
  RENEWAL_*, RECEIPT_*, MONTHS, DATE_FORMATS) содержат все 7 локалей, включая ru.
- **Magic-link с `locale:"ru"`** принимается бэкендом (живой прогон: код выдан,
  consume вернул токен), русский шаблон письма — на «ты».

**Оплаты / Т-Банк — безопасность вебхука крепкая:**

- Подпись `verify` (`tbank.py:154`): валидный токен принят; тампер `Amount`,
  отсутствие `Token`, пустой `TBANK_PASSWORD` — отвергнуты (`InvalidSignature`).
  Проверка `hmac.compare_digest` на месте.
- Живой вебхук (`POST /v1/billing/webhook`, provider=paddle): подделка без/с
  битой подписью → **401**.
- Идемпотентность: ключ `tbank:{PaymentId}:{Status}` — ретрай дублируется,
  возврат (иной Status) проходит; `webhook_event.id` PK.
- Каталог RUB: 449/449/1799/849 ₽ — совпадает с утверждёнными владельцем числами.
- Спуф `CF-IPCountry: RU` без `?country` → USD (край не доверенный, BUG-004
  фикс держится). Фаззинг `?country=` (`'; DROP`, `../`, `RUS`, `12`) → USD-фолбэк,

- `POST /checkout`: неизвестный товар → 404; billing off → 503 с явным списком
