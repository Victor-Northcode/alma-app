# QA / Security Audit — Alma

ID отчёта: 550775 · Дата: 2026-08-29 · Тестировался локальный инстанс.

Стенд: backend FastAPI на `http://127.0.0.1:8018` (SQLite, dev), сайт Next.js
на `http://127.0.0.1:3001`. Flutter-приложение (единственное отгружаемое)
на Windows не запускается (нет симулятора iOS) — оценивалось статикой и через
общий backend. Генеративные вызовы (`/v1/readings`, `/v1/chat`) намеренно не
нагружались боевым трафиком: в `.env.local` лежит рабочий `ANTHROPIC_API_KEY`,
и каждый вызов — реальные деньги владельца.

Общая оценка: **backend необычно зрелый по безопасности** — классические дыры
(IDOR, реплей вебхуков, подделка токена, инъекции, path traversal, заголовки,
CORS) закрыты и задокументированы. Реальные дефекты сосредоточены в двух местах:
**гонки «проверил-и-сделал» между воркерами gunicorn** и **доверие к
клиент-подделываемым «edge»-заголовкам**.

## HIGH

### BUG-001 — Обход дневной квоты вопросов и месячного бюджета генераций (гонка между воркерами)
Приоритет: HIGH
**[ИСПРАВЛЕНО частично — квота вопросов; месячный бюджет намеренно оставлен]**

*Квота вопросов (закрыта).* `_answer_one_turn` резервирует слот **до** генерации
атомарным `counters.spend_and_check` (прибавить-и-проверить одним запросом,
одинаково на всех воркерах) вместо чтения воротами и записи после ответа. Слот
возвращается `counters.refund`, если ход оказался приветствием или не состоялся
(во всех пяти ветках сбоя генерации — `_give_back_reserved`). Попроцессный
`_chat_slot` остаётся для порядка сообщений, но счёт вопросов больше от него не
зависит. Проверено: `test_two_questions_at_once_cannot_both_spend_the_only_one_left`,
`test_a_greeting_does_not_spend_the_one_welcome_question`,
`test_a_refused_chat_turn_gives_the_reserved_question_back` (новый),
`test_the_free_question_limit_is_real` — 89 тестов чата/квоты зелёные.

*Месячный бюджет (оставлен намеренно).* Его гонка — «прочитать сумму, сравнить»
в `ai/cost.guard_month` — **осознанное решение владельца**, задокументированное
в `db/counters.py` (раздел про снятый `charge_and_check_month`): резерв денег
имеет собственную цену (незакрытая бронь навсегда удорожает аккаунт, ветка отказа
без возврата отрезает платящего подписчика), а перелёт ограничен «одновременность
× стоимость вызова — центы против долларового потолка, раз в месяц». Реализовать
денежный резерв — значит переспорить владельца по вопросу, который он уже решил;
оставлено как есть (правило 5).
Где: `backend/alma/api/routers/readings.py:251` (`_chat_slot`), `:3076` (чтение
квоты), `:3590` (инкремент после генерации); прод-воркеры — `alma/api/deps.py:154`.

Проблема: `_chat_slot` — это **модульный `asyncio.Lock` в памяти процесса**
(`_CHAT_LOCKS[user_id] = asyncio.Lock()`). Прод — gunicorn по числу ядер (в
докстринге прямо: «на восьмиядерной машине восемь процессов»). Замок сериализует
ходы беседы только **внутри одного воркера**. При этом решение о квоте —
«проверил-и-сделал» с разрывом 10–40 c:
```
asked = await _asked(...)          # чтение (txn 1), readings.py:3076
if asked >= allowance.limit: 429
# ...генерация модели, 10-40 c, без межпроцессного замка...
if reply.spends_a_question:
    asked = await _count(...)      # инкремент (txn 3), readings.py:3591
```
`counters.add` атомарен на самом инкременте, но **чтение-ворота и инкремент не
атомарны между воркерами**, а единственный сериализатор (`_chat_slot`) —
попроцессный.

Как воспроизвести: аккаунт со свободной квотой (напр. 3/день) шлёт ~20
параллельных `POST /v1/chat` с одним и тем же bearer-токеном. Запросы
раскладываются по 8 воркерам, каждый видит счётчик **до** инкремента, все
проходят ворота, все генерируют платный ответ и лишь потом инкрементят. Итог:
N платных генераций там, где оплачена 1–3. Тем же путём переполняется
`_guard_month`/`_spend` (`readings.py:2217`, `:3596`) — месячный бюджет тира
превышается в разы.
```
for i in $(seq 20); do curl -s -H "Authorization: Bearer $TOK" \
  -H 'content-type: application/json' \
  -d '{"message":"read my chart","locale":"en"}' \
  http://host/v1/chat & done
```
Ожидается: не более `allowance.limit` платных генераций на аккаунт за окно.
Фактически: до ×(число воркеров) генераций и списаний.
Доказательство: `qa_evidence/chat_lock_perprocess.txt` (код `_chat_slot` +
докстринг про 8 воркеров). **Динамически не выполнялось — сжигает реальный
бюджет Anthropic; дефект подтверждён по коду.**
Что исправить: заменить попроцессный `asyncio.Lock` на межпроцессную блокировку
на `user.id` (SQL advisory-lock / строка-семафор в БД, как уже сделано для
`rate_window`) на весь путь «чтение квоты → генерация → инкремент»; либо
инкрементить квоту **атомарно до генерации** (резервировать слот) и возвращать
при отказе. Файл `readings.py`, обёртка вокруг `_chat_slot` и ворот `:3076`.

### BUG-002 — Двойное списание месячного парного кредита (одна включённая пара → два бесплатных отчёта $4.99)
Приоритет: HIGH
**[ИСПРАВЛЕНО]** `credits.spend` списывает кредит атомарным
`UPDATE pair_credit SET used = used + 1 WHERE used < granted RETURNING`
(`billing/credits.py`): грант выдаётся только если апдейт затронул строку, иначе
`None`. Окно «прочитал used=0 → выдал грант → записал used=1» закрыто. Проверено:
`tests/test_pair_credits.py` (32 pass, инвариант «второй кредит в периоде → None,
used==1» держится).
Где: `backend/alma/billing/credits.py:216` (`spend`, инкремент `row.used`),
`backend/alma/api/routers/readings.py:1406` (`_pair_credit_or_paywall`), `:749`
(незапертый `session_scope` в `read`).

Проблема: `credits.spend` делает **read-modify-write без атомарности и без
per-user замка**:
```
if row is None or (row.used or 0) >= (row.granted or 0): return None
row.used = (row.used or 0) + 1        # lost update при гонке
grant = await entitlements.grant(... pair:{profile_id} ...)
```
Более поздний `_write_lock` (`readings.py:823`) ключуется на `chapter+calc_key`,
который **различается для разных партнёров**, и срабатывает уже после списания
кредита — то есть не защищает.

Как воспроизвести: подписчик с 1 включённым парным кредитом в месяц шлёт
параллельно два `POST /v1/readings {"system":"compatibility","partner_profile_id":A}`
и `...partner_profile_id:B` (оба профиля свои). Обе транзакции читают
`used=0 < granted=1`, обе выдают вечный грант `pair:{A}` и `pair:{B}`. Остаётся
`used=1` при **двух** бессрочных грантах → два включённых отчёта за один кредит.
Ожидается: ровно 1 грант на 1 кредит.
Фактически: 2+ гранта.
Доказательство: `qa_evidence/pair_credit_race.txt` (код `credits.spend`).
Динамически не выполнялось: локально не сконфигурирован процессор/подписка;
дефект подтверждён по коду.
Что исправить: в `credits.spend` инкрементить `used` атомарным
`UPDATE ... SET used = used + 1 WHERE used < granted RETURNING` и выдавать грант
только если апдейт затронул строку; либо взять межпроцессный per-user замок на
всю операцию. Файл `backend/alma/billing/credits.py:232`.

## MEDIUM

### BUG-003 — Все per-source потолки обходятся ротацией клиент-подделываемого заголовка `CF-Connecting-IP`
Приоритет: MEDIUM (HIGH, если origin достижим в обход CDN)
**[ИСПРАВЛЕНО]** введена настройка `ALMA_TRUSTED_EDGE` (default `false`,
`config.py`). `deps.request_source` читает `CLIENT_IP_HEADERS` только при
`trusted_edge=true`; иначе берёт исключительно адрес сокета. На прямом инстансе
подделанные адреса ложатся в один ключ и упираются в тот же потолок. Прод за
nginx/Cloudflare ставит флаг (задокументировано в `.env.example` и
`docs/DEPLOY.md`). Проверено:
`test_the_edge_source_header_is_ignored_when_not_behind_a_trusted_edge` (падает
на старом коде), `test_each_source_carries_its_own_budget` (за краем — работает).
Где: `backend/alma/api/deps.py:94`–`147` (`request_source`); потребители —
`deps.py:719` (guest_mint), `routers/auth.py:198` (magic-link),
`routers/admin.py:93` (admin login 5/час), `deps.py:799` (systems calc).

Проблема: `request_source` берёт первый из
`cf-connecting-ip / true-client-ip / fastly-client-ip / x-real-ip` — все
присылаются клиентом — и лишь потом сокет. Каждый потолок ключуется на этом
значении. Заголовок доверенный только если край **перезаписывает** его; на
инстансе, доступном напрямую (или где CDN не Enterprise и не чистит
`true-client-ip`/`x-real-ip`), значение подделывает атакующий.

Как воспроизвести (подтверждено на стенде):
```
# фикс. IP: source-лимит magic-link (10/час) срабатывает
203.0.113.50 → 202×10, затем 429, 429
# ротация IP: тот же лимит полностью снят
198.51.100.$i → 202×12  (все проходят)
```
Ожидается: потолок держит источник независимо от присланных заголовков.
Фактически: смена одного заголовка на запрос обнуляет потолок — открывает
брутфорс `/admin/api/login`, безлимитную ротацию гостей (=месячные бюджеты) и
перебор кодов из письма.
Доказательство: `qa_evidence/ratelimit_bypass.txt` (вывод обоих циклов).
Что исправить: не доверять заголовкам по умолчанию. Ввести настройку
`ALMA_TRUSTED_EDGE=true` — только при ней читать `CF-*`; иначе брать адрес
сокета. На проде за Cloudflare оставить в списке **только** `cf-connecting-ip`
(его CF гарантированно перезаписывает) и убрать `true-client-ip`/`x-real-ip`/
`fastly-client-ip`, если они не чистятся краем. Файл `deps.py:94` (`CLIENT_IP_HEADERS`).

### BUG-004 — Клиентский заголовок `CF-IPCountry` управляет валютой и ценой каталога
Приоритет: MEDIUM (потенциально HIGH — недоплата, если origin достижим напрямую)
**[ИСПРАВЛЕНО]** тем же флагом `ALMA_TRUSTED_EDGE`. `deps.edge_country` читает
`CF-IPCountry`/`region.from_headers` только за доверенным краем; иначе страна —
из `?country=` (оценка для витрины) или USD-фолбэк, заголовок игнорируется.
Подделка `CF-IPCountry: IN` больше не превращает каталог в рупии. Проверено:
`test_the_edge_header_is_ignored_when_the_deployment_is_not_behind_one` (падает на
старом коде, INR вместо USD); `test_the_catalogue_prices_the_country_the_edge_reports`
(за краем — цена по стране). Замечание отчёта про фактическую недоплату на
процессоре остаётся вне стенда (checkout=503 без ключей).
Где: `backend/alma/region.py:117`–`147` (`from_headers`/`resolve`),
`backend/alma/api/routers/billing.py` (catalogue), `alma/billing/provider.py:999`
(`_the_money_covers_it`).

Проблема: страна берётся из клиент-присылаемого `CF-IPCountry`, и она выбирает
валюту и локальную цену. Подтверждено на стенде:
```
(нет заголовка)       → USD  $4.99
CF-IPCountry: IN      → INR  ₹109
CF-IPCountry: BR      → BRL  R$ 12,90
CF-IPCountry: GB      → GBP  £4.99
```
Как воспроизвести: `curl -H "CF-IPCountry: IN" http://host/v1/billing/catalogue`
→ каталог в INR по PPP-цене. По разбору кода `_the_money_covers_it`
(`provider.py:1030`) сверяет оплату против `product.cents_in(resolved_currency)`
— то есть подделка страны ведёт к валидной **недоплате** дешёвой ценой за
продукт, стоящий $4.99.
Ожидается: валюта — из доверенного края (или страны Apple-аккаунта в мобайле),
не из присланного заголовка.
Фактически: цену выбирает отправитель запроса.
Доказательство: `qa_evidence/currency_spoof.txt`.
Замечание: денежный путь (`/v1/billing/checkout`) на стенде отдаёт 503 (нет
`PADDLE_API_KEY`), поэтому фактическая недоплата **требует проверки на
сконфигурированном процессоре** — подтверждена только управляемость цены.
Что исправить: та же настройка `ALMA_TRUSTED_EDGE`; на web-чекауте валюту брать
из доверенного источника, а не из заголовка запроса. Файл `region.py:117`.

### BUG-005 — Пароль админки — голый несолёный SHA-256
Приоритет: MEDIUM
**[ИСПРАВЛЕНО]** пароль хранится солёным `hashlib.scrypt` (новый модуль
`auth/admin_password.py`, формат `scrypt$n$r$p$salt$hash`, stdlib, без GPL/сторонних
зависимостей). `admin.login` сверяет `verify()` (constant-time), а старый голый
SHA-256 отвергает с логом «перегенерируй». Хэш генерит `python -m tools.admin_password`
(скрытый ввод пароля владельцем). Проверено:
`test_the_stored_hash_is_salted_and_slow_not_bare_sha256`,
`test_a_legacy_sha256_hash_is_refused_not_accepted`, весь `tests/test_admin.py`
(12 pass). Задокументировано в `.env.example` и `docs/DEPLOY.md`.
Где: `backend/alma/api/routers/admin.py:105`.

Проблема: `typed = hashlib.sha256(payload.password.encode()).hexdigest()` —
сравнение `hmac.compare_digest` закрывает тайминг, но хранимый хэш — **несолёный
быстрый SHA-256**. В связке с BUG-003 (обход троттла 5/час) — реальный онлайн-
перебор пароля не-высокой энтропии. Одна админ-сессия даёт грант `system="*"` на
любую почту (`admin.py:184`).
Как воспроизвести: код-ревью; на стенде админка отдаёт 503 (хэш не задан в dev).
Ожидается: медленный солёный KDF (scrypt/argon2/bcrypt).
Фактически: SHA-256 без соли.
Доказательство: `qa_evidence/admin_login.txt`.
Что исправить: хранить `scrypt`/`argon2id` хэш пароля (stdlib `hashlib.scrypt`),
сверять им; файл `admin.py:105` и генерация хэша в конфиге.

### BUG-006 — `/v1/billing/declined`: «одноразовый» даунселл переигрывается гонкой
Приоритет: LOW
**[ИСПРАВЛЕНО]** оффер столбится атомарным `counters.bump_flag` (новый примитив
в `db/counters.py`: `INSERT … ON CONFLICT DO UPDATE SET count = count + 1
RETURNING` по заданному id, без окна чтение-запись). Скидка отдаётся ровно тому
вызову, чей результат равен 1; проигравший заезд видит `>1` и получает
«already offered once». Проверено: `test_the_downsell_is_offered_exactly_once`.
Где: `backend/alma/api/routers/billing.py:1977`.
Проблема: чтение-затем-запись `row.count = (row.count or 0) + 1` без атомарного
`counters.add` и без замка. Два параллельных `POST /v1/billing/declined
{"system":"natal"}` оба видят `count==0`, оба отдают скидку; lost update оставляет
`count==1`. Нарушает заявленное в комментарии «ровно один раз, навсегда».
Доказательство: `qa_evidence/pair_credit_race.txt` (тот же класс, отдельный код).
Что исправить: атомарный `counters.add`/`UPDATE ... RETURNING` вместо
read-modify-write. Файл `billing.py:1994`.

### BUG-007 — `/v1/billing/checkout` без проверки «уже куплено» → двойная оплата
Приоритет: LOW
**[ИСПРАВЛЕНО]** перед открытием чекаута вызывается новый
`entitlements.already_owned`; уже купленный продукт → 409 `already_owned`.
Осторожно, чтобы не сломать законное: расходуемая проверка пары не блокируется
(покупается на каждого партнёра); дверь/бандл блокируются только против *вечного*
держания, а не подписки (купить дверь про запас, будучи подписчиком, законно —
подписка истекает); подписка — только против той же живой повторяющейся модели
(апгрейд остаётся открытым). Проверено:
`test_a_product_already_owned_does_not_open_a_second_checkout`.
Где: `backend/alma/api/routers/billing.py:254`; гейт — только
`entitlements.may_be_offered` (`auth/entitlements.py:440`, проверяет лишь
`on_the_shelf`, не владение).
Проблема: владелец `door.natal` или живой подписки может открыть второй чекаут
на тот же продукт; вебхук впишет второй one-time грант либо **вторую параллельную
подписку** (`grant` ключуется на новый `subscription_id`). Вред покупателю /
поток возвратов, не потеря для бизнеса.
Что исправить: перед открытием чекаута отказывать, если продукт уже во владении
(`entitlements` содержит систему/живую подписку). Файл `billing.py:254`.

### BUG-008 — `GET /v1/account/export` доступен гостю
Приоритет: LOW
**[НЕ ИСПРАВЛЕНО: намеренное поведение, уже задокументировано в коде]**
Экспорт отдаёт гостю **его же** данные и открыт гостю сознательно —
`account.py:52-59` объясняет это подробно: гостевой аккаунт держит дату и
полные координаты рождения, а почту у него никто не спрашивал; потребовать её,
чтобы человек прочитал свой собственный файл, — значит просить *больше* личных
данных как плату за просмотр уже собранных. Та же логика, что у `delete` (её
владелец намеренно сменил с `Account` на `CurrentUser`, `account.py:75-83`) — и
та же причина отклонения в Play. IDOR тут нет: возвращается ровно аккаунт за
токеном. Смена на `require_account` сломала бы privacy-замысел продукта, поэтому
код не тронут; отчёт сам допускал «задокументировать намеренность» — она
задокументирована.
Где: `backend/alma/api/routers/account.py` (маршрут export).
